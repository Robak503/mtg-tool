## Problem Statement

Karn currently suggests cards from the sky. He doesn't know which ones the user
owns. Every real EDH player has two questions Karn cannot answer today:

1. "Can I build this deck with cards I already have?"
2. "I have $X to spend, what should I add?"

The same blind spot infects every other agent. Tibalt can't roast a real
collection. Jace can't answer "do I own anything that does X?" The product
speaks fluently about Magic in the abstract and is silent about the user's
actual cards.

The fix is a real collection layer. Not an integration with Moxfield or
Archidekt. A native, local-first collection that lives in AppData, displays
in a tab, and gets read by every agent the user already paid for.

---

## What Makes This Cool

- Every existing agent gets sharper for free. Karn marks every suggestion
  "owned" or "$X to acquire." Tibalt roasts hoarders. Jace queries on demand.
- The bundled Scryfall art crops finally do real work. The collection tab is
  visually dense, fast, and feels like a real EDH companion instead of a chat
  log.
- It's the foundation every later feature stands on. Bracket coach needs it
  to suggest realistic upgrades. Pod simulator wants to test real decks built
  from real cards. Notebook references cards you own. Camera scan (later
  phase) drops cards into this directly.
- No external service. No login. No sync conflicts. The user's collection
  lives on their disk and never leaves it.
- It is the thing a SaaS competitor literally cannot ship as well as you,
  because they don't have bundled card data plus free local compute plus a
  desktop shell. You do.

---

## Constraints

- Local-first. No external API in the steady-state path. Scryfall data is
  already bundled and used.
- Reads/writes through `paths.js` only. Never `process.cwd()` or raw
  `__dirname`.
- Must work in dev mode (`npm run dev`) and in the packaged `.exe`.
- Storage uses the writable AppData location:
  `%APPDATA%\com.colton.mtg-tool\data\collection.json`.
- Performance target: 5,000+ cards must scroll without jank. 500-card CSV
  import completes in under 10 seconds.
- Test coverage required for the data layer (vitest) and at least an import
  smoke test for every new `/api/collection/*` route (the
  `/api/engine` regression rule from CLAUDE.md §5 #10).

---

## Premises

1. The collection is a **data layer**, not an agent. The user-facing surface
  is a tab. Every existing agent reads from the layer. No new agent
  persona is created.
2. Storage is a single JSON file under AppData until size becomes a
  problem. 10K cards in JSON is fine. SQLite is the long-term answer but
  not a v1 problem.
3. Cards are tracked at the **Scryfall printing level** (set + collector
  number), not just oracle level. A foil Hullbreacher from Commander
  Legends is a different row from a non-foil Hullbreacher from Double
  Masters. But search and agent integration default to **oracle id**, so
  Karn doesn't care which printing you own when judging "do you have a
  draw spell."
4. CSV import accepts Deckbox and Moxfield formats. Both are common,
  both are standard, both are easy to parse.
5. Cross-deck conflict detection is computed **on read**, not stored. The
  truth lives in `decks.local.json` + `collection.json`. The UI joins them
  virtually.
6. Price tracking uses the bundled Scryfall snapshot. Refreshed on sync.
  Historical price log is append-only to a separate file so the main
  collection.json stays small and stable.

## Approaches Considered

### Approach A: Single-pane maximalist

One big collection tab with everything stuffed in: grid view, filters
inline, add-card form at the top, detail panel below, Karn suggestions
pinned to a sidebar, price chart at the bottom.

**Effort**: M. **Risk**: Med. **Reuses**: existing card-detail components,
oracle-index search.

**Pros**:
- Everything is one screen, no navigation needed
- Fast to build because there's no routing or state coordination

**Cons**:
- UI bloat will become a problem at v2 when wishlist + price history land
- Hard to keep the grid clean when filters and forms compete for the same
  vertical space
- Doesn't match the existing MTGAssistant.jsx idiom (which uses sidebars
  + drawers, not stuffed panes)

### Approach B: Tab with sub-modes

Main "Collection" tab with mode toggles at the top:
Browse / Build-from-Collection / Cross-Deck / Wishlist / Price Watch.
Each mode is its own view sharing the same underlying data layer.

**Effort**: M-L. **Risk**: Low. **Reuses**: oracle-index, deck join logic.

**Pros**:
- Clean separation of concerns, each mode is focused
- Easy to grow with future modes (Combo-Audit, Foil-Tracker, etc)

**Cons**:
- Mode toggling is friction. Users want to flip from "Browse" to "what
  decks is this in" without losing context
- Five modes is a lot of nav surface for what's conceptually one feature

### Approach C: Tab + contextual drawers (recommended)

One main Collection tab with a grid as the primary view. Contextual drawers
slide in for secondary tasks:
- **Right drawer**: card detail (Oracle text, rulings, prices, which decks
  this is in)
- **Top drawer**: filters and sort (collapsible)
- **Bottom drawer**: Karn suggestions / Tibalt roast / cross-deck conflicts
  (whichever is contextually relevant)
- **Modal**: Add card, CSV import, wishlist editor

**Effort**: M. **Risk**: Low. **Reuses**: existing MTGAssistant.jsx pattern
(main pane + sidebars), oracle-index search, card detail components.

**Pros**:
- Matches the existing app's UI language, no learning curve
- The grid stays clean because secondary stuff is in drawers
- Grows gracefully: future features become new drawer modes, not new tabs
- One screen, one mental model, zero mode-flipping

**Cons**:
- Drawer animation work needs to be smooth or it feels janky
- Mobile layout will eventually need a different solution (not a v1
  problem)

---

## Recommended Approach: C

The drawer model fits the project's existing UI grammar, keeps the grid
clean, and scales without re-architecting. Approach A is faster but a
short-term win. Approach B is clean but the mode toggle is a UX tax the
user will pay every time they want to flip between browse and conflict
view.

## Data Model

`%APPDATA%\com.colton.mtg-tool\data\collection.json`:

```jsonc
{
  "version": 1,
  "updatedAt": "2026-05-27T18:00:00Z",
  "cards": [
    {
      "scryfallId": "abc-123-...",
      "oracleId": "def-456-...",
      "name": "Sol Ring",
      "setCode": "C21",
      "collectorNumber": "256",
      "quantity": 4,
      "foilQuantity": 1,
      "condition": "NM",
      "addedAt": "2025-12-01T10:00:00Z",
      "notes": "",
      "wishlist": false
    }
  ]
}
```

Notes:
- `quantity` = non-foil count. `foilQuantity` = foil count. Two integer
  fields on one row, not separate rows.
- `condition` applies to the whole stack as a coarse signal. If the user
  cares about per-copy condition tracking, that's a v2 extension where the
  row becomes per-copy.
- `wishlist: true` means owned=0 but track this card for price watch and
  "want it" purposes. Same schema, different filter.
- `version: 1` lets future migrations branch cleanly.

`%APPDATA%\com.colton.mtg-tool\data\collection-prices.jsonl`:

Append-only price snapshots, one JSON object per line:

```jsonc
{"snappedAt":"2026-05-27","oracleId":"def-456","usd":3.50,"usdFoil":12.00}
```

Written by the existing sync pipeline. Used for "your collection gained
$X this month" stats. Kept separate so collection.json doesn't bloat.

## Agent Integration

This is the actual unlock.

`collectionContext.js` exposes:

```js
loadCollection(): Promise<Collection>
collectionSummary(c): { totalCards, uniqueOracles, colorBreakdown, topByCount, totalValueUsd }
isOwned(c, oracleId, minQty=1): boolean
ownedCountByOracle(c, oracleId): { regular, foil }
buildOwnedSet(c): Set<oracleId>      // for fast lookups
crossDeckUsage(c, decks): Map<oracleId, { ownedQty, usedQty, deckIds[] }>
conflicts(c, decks): Array<{ oracleId, ownedQty, usedQty, deckIds[] }>
```

Each agent's system prompt builder calls `collectionSummary()` and
injects:

```
COLLECTION SUMMARY (read-only context):
- 1,847 unique cards owned (3,204 total counting copies)
- Color breakdown: W 18%, U 22%, B 19%, R 15%, G 19%, C 7%
- Top owned: Sol Ring x4, Command Tower x3, Counterspell x3, ...
- Estimated value: $4,832 USD
```

For Karn's suggestion-rendering, the response is post-processed: each
suggested card is checked against `isOwned()` and annotated:

```
SUGGESTED ADDS
[[Smothering Tithe]] ✓ owned
[[Rhystic Study]] $34.50 to acquire
[[Esper Sentinel]] ✓ owned (1 copy, deck conflict with Atraxa)
```

For the new **"Build from my collection"** Karn mode: a new starter prompt
in the chat picker. Karn's system prompt switches to collection-constrained
mode and his suggestion engine pre-filters to the owned set. Stretch picks
that aren't owned get a separate, optional "$X stretch goals" section.

For **Tibalt collection roast**: new endpoint `/api/tibalt/roast-collection`.
Tibalt gets the summary + outliers (most-owned card, weirdest single-copy
inclusion, most expensive card-you-don't-have-in-any-deck, biggest gap in
a color). Returns ~200 words of surgical disrespect.

## Cross-Deck Tracking

Computed on read, not stored. On every load of `CollectionView` or a
deck view:

```js
const collection = await loadCollection();
const decks = await loadDecks();
const conflicts = computeConflicts(collection, decks);
```

`conflicts` returns rows where `sum(deck uses) > collection.quantity`.

UI surfaces:
- On a card in the grid: red badge if conflicted ("used in 4 decks, own 2")
- On a deck view: warning at the top listing conflicts
- In the Collection bottom drawer when conflicts exist: full list with
  jump-to-deck links

Why on-read: deck contents change constantly. Storing this would create
sync bugs. Computing is cheap (one O(n) pass over the deck cards).

## CSV Import

Supports two formats out of the gate:

**Deckbox**: `Count,Name,Edition,Condition,Language,Foil,Signed,Artist Proof,Altered Art,Misprint,Promo,Textless,My Price`

**Moxfield**: `"Count","Name","Edition","Condition","Language","Foil","Tags","Last Modified"`

Flow:
1. User uploads CSV via `CollectionImportModal`
2. Backend (`csvImport.js`) parses, autodetects format
3. For each row, match against bundled Scryfall data:
   - First try: name + set code (high confidence)
   - Fallback: name only, use most recent printing
   - Unmatched: shown in a "review" list, user can resolve manually
4. Preview screen shows: N cards matched, M unmatched, X duplicates merged
   into existing collection
5. User confirms, write happens transactionally (write to temp file, atomic
   rename)

Performance: 500-card CSV must complete in under 10 seconds. Parser is
streaming, lookups are against an in-memory oracle-index loaded once.

## Price Tracking

Bundled Scryfall data already contains `prices.usd` and `prices.usd_foil`
per printing. The existing sync pipeline writes these on every refresh.

New behavior: after each sync, write a `collection-prices.jsonl` entry per
owned oracle id. This is the snapshot. Over time, this file builds a
history.

Stats endpoint `/api/collection/stats` computes:
- Current total value (sum over owned cards)
- Delta vs. 30 days ago, 90 days ago, 365 days ago (if data exists)
- Top gainers / losers in the last 30 days

UI surfaces this on the Collection home: a quiet stat block. "Your
collection is worth $4,832. Up $147 this month." Tasteful, not financial-
advisor-y.

---

## Wishlist

Same schema, `wishlist: true`, `quantity: 0` (or `foilQuantity: 0`).

Filter view: "Wishlist." Shows wanted cards with current price. Total
wishlist cost displayed at the top: "Your wishlist would cost $234."

Wishlist cards get price-watched too. "Rhystic Study on your wishlist
dropped $5 this month."

When the user adds a wishlist card to the real collection (acquires it),
the row is updated: `wishlist: false`, `quantity` incremented.

## Open Questions

1. Should "build from my collection" Karn mode allow stretch goals
  (cards not owned but strongly recommended)? Current design says **yes,
  with a clear separate section**. The deckbuilder use case demands it.
2. Should we warn on import when adding a card already in the collection,
  or auto-merge quantities? Current design says **auto-merge with a
  summary in the preview**.
3. Should foil and non-foil be the same row or separate rows? Current
  design says **same row, two integer fields**. Cleaner schema, no
  duplicate detection logic.
4. Cross-deck conflict UI: badge-on-grid vs. only-show-in-conflicts-drawer?
  Current design says **both**. Badge for at-a-glance, drawer for the
  full list.
5. Should the Tibalt collection roast be a one-shot or saved to history
  (like deck roasts are saved to deck memory)? Current design says **save
  to a new `collection-roasts.json`** so Tibalt can compare collection
  drift over time later. "Six months ago you owned 23 Sol Rings. You now
  own 31. Help."

## Success Criteria

- Add a card via search-to-add: under 5 seconds keystroke-to-saved
- Browse 5,000 cards in the grid with smooth scroll (60fps, virtualized)
- All Karn suggestions in any conversation show correct owned/needed
  annotations
- CSV import of a 500-card Deckbox export completes in under 10 seconds
  with a clean preview
- Cross-deck conflict detection runs in under 100ms when opening a deck
  view
- Tibalt collection roast returns within 30 seconds on Ollama (local)
- "Build from my collection" Karn mode returns a 100-card list within 60
  seconds, all entries marked owned + stretch goals marked separately
- Wishlist persists across launches and price-tracks correctly on each
  sync

## What This Unblocks

Once Collection ships:

- **Bracket coach** (next theme) becomes realistic. Bracket suggestions
  can recommend "to push this from bracket 2 to bracket 3, add these 5
  cards, you own 3 of them already."
- **Evolution memory + weekly digest** gets a richer signal. Snapshots
  include collection state, not just deck state. "You acquired 7 cards
  this week. Three of them slot directly into your Atraxa list."
- **Pod simulator** lets you test decks built from real cards, which is
  the actual use case.
- **Camera scan (physical bridge phase)** plugs into this directly. Snap
  a card, row gets added. No re-architecting needed because the schema
  already supports it.
- **Notebook + local social** reference cards you own, which makes the
  references mean something instead of being abstract.

## Appendix: The Full Roadmap

For reference, the broader plan from this office hours session, in order:

2. **Bracket coach + Evolution memory** — Bracket assessment, weekly

  Jace's voice from the game log.

require external services.
