## Problem Statement

Karn currently suggests cards from the sky. He doesn't know which ones the user
owns. Every real EDH player has two questions Karn cannot answer today:

1. "Can I build this deck with cards I already have?"
2. "I have $X to spend, what should I add?"

The same blind spot infects every other agent. Tibalt can't roast a real
collection. Jace can't answer "do I own anything that does X?" The product
speaks fluently about Magic in the abstract and is silent about the user's
actual cards.

The fix is a real collection layer. Not an integration with Moxfield or
Archidekt. A native, local-first collection that lives in AppData, displays
in a tab, and gets read by every agent the user already paid for.

---

## What Makes This Cool

- Every existing agent gets sharper for free. Karn marks every suggestion
  "owned" or "$X to acquire." Tibalt roasts hoarders. Jace queries on demand.
- The bundled Scryfall art crops finally do real work. The collection tab is
  visually dense, fast, and feels like a real EDH companion instead of a chat
  log.
- It's the foundation every later feature stands on. Bracket coach needs it
  to suggest realistic upgrades. Pod simulator wants to test real decks built
  from real cards. Notebook references cards you own. Camera scan (later
  phase) drops cards into this directly.
- No external service. No login. No sync conflicts. The user's collection
  lives on their disk and never leaves it.
- It is the thing a SaaS competitor literally cannot ship as well as you,
  because they don't have bundled card data plus free local compute plus a
  desktop shell. You do.

---

## Constraints

- Local-first. No external API in the steady-state path. Scryfall data is
  already bundled and used.
- Reads/writes through `paths.js` only. Never `process.cwd()` or raw
  `__dirname`.
- Must work in dev mode (`npm run dev`) and in the packaged `.exe`.
- Storage uses the writable AppData location:
  `%APPDATA%\com.colton.mtg-tool\data\collection.json`.
- Performance: 5,000-row grid renders at 60fps via `@tanstack/react-virtual`
  with art crops lazy-loaded from bundled file paths via Tauri
  `convertFileSrc`. 500-card CSV import completes in under 10 seconds.
- Test coverage required for the data layer (vitest) and at least an import
  smoke test for every new `/api/collection/*` route (CLAUDE.md §5 #10).
- All writes to `collection.json` go through a single atomic helper
  (temp + rename). No route writes the file directly.

---

## Premises

1. The collection is a **data layer**, not an agent. The user-facing surface
   is a tab. Every existing agent reads from the layer. No new agent
   persona is created.
2. Storage is a single JSON file under AppData until size becomes a problem.
   10K cards in JSON is fine. SQLite is the long-term answer but not a v1
   problem.
3. Cards are tracked at the **Scryfall printing level** (set + collector
   number) per row. Within a row, a `stacks` array represents multiple
   finishes (`nonfoil` / `foil` / `etched`) with per-stack condition. Search
   and agent integration default to **oracle id**, so Karn doesn't care
   which printing you own when judging "do you have a draw spell."
4. CSV import accepts Deckbox and Moxfield formats. Both are common, both
   are standard, both are easy to parse.
5. Cross-deck conflict detection is computed **on read**, not stored. The
   truth lives in `decks.local.json` + `collection.json`. The UI joins them
   virtually with memoization keyed on both files' `updatedAt`.
6. Price tracking uses the bundled Scryfall snapshot. Refreshed on sync.
   Historical price log is append-only to a separate file so the main
   collection.json stays small and stable. Written by sync scripts only;
   the app process reads only.
7. The bundled Scryfall data is exposed via **two indexes**: the existing
   oracle-level `oracle-index.json` (rules/synergy questions, already
   loaded by `cardIndex.js`) and a new printing-level
   `printings-index.json` (Collection's CRUD, grid display, CSV matching).
   See Step 0 below.

## Step 0 — Prerequisite: Build the Printing-Level Index

This must ship before any Collection code lands.

### Why this exists

`oracle-index.json` (the slim ~30 MB file actually loaded by
`cardIndex.js`) has only oracle-level fields: name, oracle_id, type_line,
oracle_text, mana_cost, cmc, color_identity, legalities, layout, keywords.

It does NOT have: `set`, `collector_number`, `id` (scryfallId),
`image_uris`, or `prices`.

Collection needs all of those. Without them: CSV matching by set+collector
fails, the grid can't render art crops, price tracking has no per-printing
source, and the schema fields `scryfallId` / `setCode` / `collectorNumber`
are unfillable on add.

### The source data

`app/data/scryfall-bulk/unique_artwork.json` (~252 MB) already syncs as
part of the release pipeline. It has every field needed:
`id`, `oracle_id`, `name`, `set`, `collector_number`, `finishes`,
`layout`, `image_uris.art_crop` (top-level OR via `card_faces[0]`),
`prices.usd`, `prices.usd_foil`, `prices.usd_etched`.

It cannot be loaded via plain `JSON.parse` — at 252 MB it exceeds Node's
`ERR_STRING_TOO_LONG` threshold (0x1fffffe8 chars). Must be streamed.

### The output

`app/data/scryfall-bulk/printings-index.json` (target ≤80 MB).

Two indexes inside:
- By `${set}:${collector_number}` (lowercase set, exact collector) — for
  CSV matching.
- By `id` (scryfallId) — for direct row joins.

Fields per printing (strict allowlist to keep the file small):
- `id`, `oracleId`, `name`, `set`, `collectorNumber`
- `finishes` (array of "nonfoil" / "foil" / "etched" as Scryfall reports)
- `layout`
- `artCropPath` (a relative path the app resolves via `convertFileSrc`;
  picks top-level `image_uris.art_crop` first, then
  `card_faces[0].image_uris.art_crop` for DFCs)
- `prices`: `{ usd, usdFoil, usdEtched }` (nulls preserved)

### The build script

`app/scripts/build-collection-printings-index.cjs`.

- Uses a streaming JSON parser (`stream-json` package, ~30 KB) or the
  same pattern as `build-oracle-index.cjs` already in repo
- Streams `unique_artwork.json` array, projects per-printing fields,
  emits the final index as a single JSON object (the two indexes are
  small enough at the projected size to fit in memory at runtime).
- Vitest smoke test: run on a 10-row fixture, assert structure.

### Wiring

- New step in `.github/workflows/release.yml` between "Build slim oracle
  index" and "Build rules retrieval index"
- New action option in `/api/sync-data` for in-app rebuild
- Loaded once at server start via
  `app/src/lib/server/printingIndex.js` (lazy on first use)

### Bundle impact

- The real bundling pipeline is `prepare-tauri-resources.cjs` (hand-picked
  `dataFiles` list under `src-tauri/resources/`), NOT
  `strip-standalone-bloat.cjs` (which just removes everything from
  `.next/standalone/data/`). Add `printings-index.json` to the dataFiles
  list, and add `build-collection-printings-index.cjs` to the bundled
  syncScripts so `/api/sync-data` can rebuild it in-app.
- Installer size budget: actual delta measured at ~18 MB (well under
  the 25 MB target).
- Art crops themselves are not bundled in v1 — bundling ~1.7 GB of art
  crops is infeasible. The index stores Scryfall CDN URLs; the runtime
  lazy-fetches on first view and caches to
  `%APPDATA%\com.colton.mtg-tool\data\art-crops\<id>.jpg`. After a card
  has been viewed once, fully offline forever. Documented as a one-shot
  network call per card-first-view (acceptable per local-first mandate
  since it's user-driven, not background sync).

## Approaches Considered (UI architecture)

### Approach A: Single-pane maximalist

One big collection tab with everything stuffed in: grid view, filters
inline, add-card form at the top, detail panel below, Karn suggestions
pinned to a sidebar, price chart at the bottom.

**Effort**: M. **Risk**: Med. **Pros**: everything on one screen, no nav.
**Cons**: UI bloat at v2, hard to keep grid clean, doesn't match
existing MTGAssistant.jsx sidebar idiom.

### Approach B: Tab with sub-modes

Main "Collection" tab with mode toggles (Browse / Build-from / Cross-Deck /
Wishlist / Price Watch). Each mode is its own view.

**Effort**: M-L. **Risk**: Low. **Pros**: clean separation. **Cons**: mode
toggling is friction, five modes is a lot of nav surface for one feature.

### Approach C: Tab + contextual drawers (recommended)

Main grid as primary view. Contextual drawers slide in:
- Right drawer: card detail (Oracle text, rulings, prices, decks-this-is-in)
- Top drawer: filters and sort (collapsible)
- Bottom drawer: Karn suggestions / Tibalt roast / cross-deck conflicts
- Modal: Add card, CSV import, wishlist editor

**Effort**: M. **Risk**: Low. **Pros**: matches existing app UI language,
grid stays clean, grows gracefully without re-architecting. **Cons**:
drawer animations need to be smooth.

---

## Recommended Approach: C

Matches the existing UI grammar, keeps the grid clean, scales without
re-architecting. A is faster short-term. B is clean but the mode toggle
is a UX tax.

## Data Model

`%APPDATA%\com.colton.mtg-tool\data\collection.json`:

```jsonc
{
  "version": 1,
  "updatedAt": "2026-05-27T18:00:00Z",
  "cards": [
    {
      "scryfallId": "abc-123-...",
      "oracleId": "def-456-...",
      "name": "Sol Ring",
      "setCode": "C21",
      "collectorNumber": "256",
      "stacks": [
        { "finish": "nonfoil", "quantity": 4, "condition": "NM" },
        { "finish": "foil",    "quantity": 1, "condition": "LP" }
      ],
      "addedAt": "2025-12-01T10:00:00Z",
      "notes": "",
      "wishlist": false
    }
  ]
}
```

Schema notes:
- One row per Scryfall printing (`scryfallId`). Same card from a different
  set = different row.
- `stacks` is an array, one entry per owned finish. Valid `finish`:
  `nonfoil`, `foil`, `etched`. Missing finishes have implicit quantity 0
  (omitted from the array).
- `condition` per stack: `NM`, `LP`, `MP`, `HP`, `DMG`. May be `null` for
  wishlist stacks (quantity 0).
- `wishlist: true` means owned = 0 across all stacks. The stacks array
  still has at least one entry indicating the **wanted** finish
  (`{finish: "foil", quantity: 0, condition: null}`). When a user updates
  any stack to quantity > 0, `wishlist` auto-flips to `false`.
- `version: 1` lets migrations branch cleanly. See "Storage and
  Concurrency" below.

`%APPDATA%\com.colton.mtg-tool\data\collection-prices.jsonl`:

Append-only, one JSON object per line, written by sync scripts only:
```jsonc
{"snappedAt":"2026-05-27","scryfallId":"abc-123","usd":3.50,"usdFoil":12.00,"usdEtched":null}
```

### Storage and Concurrency

All writes to `collection.json` flow through a single helper in
`app/src/lib/server/collectionStorage.js`:

```js
async function writeCollectionAtomic(payload) {
  const target = dataPath("collection.json");
  const tmp = `${target}.tmp.${process.pid}.${Date.now()}`;
  await fs.writeFile(tmp, JSON.stringify(payload, null, 2), "utf8");
  await fs.rename(tmp, target);
}
```

Rules:
- Every CRUD route calls `writeCollectionAtomic`. No route writes the
  file directly.
- On load, if `payload.version > 1`, throw `CollectionVersionMismatch`.
  UI surfaces: "Collection file is from a newer version of MTG Tool.
  Update to use it."
- If JSON parse fails on load, the helper:
  1. Backs up the corrupted file to
     `collection.broken-${timestamp}.json`
  2. Returns an empty collection
  3. Returns a `recoveryWarning` flag the UI shows as a toast on next
     mount
- `collection-prices.jsonl` is written **only** by sync scripts via
  `fs.appendFile` (single-writer). The app reads via a streaming line
  parser so multi-year history scales without loading the whole file.
- Multi-window note: production `.exe` is single-instance. Dev mode can
  have two tabs open against the same data dir; rely on atomic-write
  (last writer wins). Documented as "do not run two dev tabs against
  the same data dir."

## Agent Integration

The actual unlock. Must respect Ollama context limits.

`collectionContext.js` exposes:

```js
loadCollection(): Promise<Collection>
collectionSummary(c, opts?): {
  totalCards, uniqueOracles, colorBreakdown,
  topByCount, totalValueUsd
}
isOwned(c, oracleId, minQty=1): boolean     // sums across all printings + stacks
ownedCount(c, oracleId): { nonfoil, foil, etched, total }
buildOwnedSet(c): Set<oracleId>             // fast lookups
crossDeckUsage(c, decks): Map<oracleId, { ownedQty, usedQty, deckIds[] }>
conflicts(c, decks): Array<{ oracleId, ownedQty, usedQty, deckIds[] }>
```

### Prompt injection rules

These are NOT suggestions. The current agent system prompts are large
(Karn's `KARN_PROMPT` runs ~600 lines / ~7-9K tokens by itself) and the
runtime concatenates additional context blocks on top. Ollama context
windows for the models in use are typically 8K-32K. Naive injection
blows the window.

1. **Hard cap**: `COLLECTION SUMMARY` block ≤ 400 tokens (~1600 chars).
   `collectionSummary()` truncates `topByCount` aggressively to stay
   under.
2. **Location**: injected into the **user message context** (like
   `## LOCKED KARN DECK CONTEXT` already does in `agents.js`). NOT into
   the system prompt. System prompts stay stable across calls.
3. **Gating**:
   - **Karn "build from collection" mode**: always inject + full owned
     set (separate `## CONSTRAINED TO OWNED CARDS` block, up to ~2000
     oracle IDs / ~50 KB).
   - **Karn deck analysis**: inject summary only if `collection.json`
     exists with ≥10 cards. Otherwise skip.
   - **Jace**: inject summary only on collection-related intents (regex
     match on "my collection", "do I own", "what do I have", etc).
   - **Tibalt**: inject only when user explicitly clicks "Roast my
     collection" (separate endpoint — see below).
4. **Measurement**: every injection logs prompt size via existing
   `inputCharCount` path in `app/src/lib/server/modelProvider.js` and
   the `model-calls` telemetry. Verify token budgets in practice.

### Karn response post-processing

When Karn returns suggested cards, each card mention (parsed from
`[[card name]]` markup that Karn already uses) is checked against
`isOwned()` and annotated in rendered output:

```
SUGGESTED ADDS
[[Smothering Tithe]] ✓ owned
[[Rhystic Study]] $34.50 to acquire
[[Esper Sentinel]] ✓ owned (1 copy, deck conflict with Atraxa)
```

The LLM doesn't have to know inventory — the post-processor does the
lookup. Robust to hallucination.

### "Build from my collection" Karn mode

New chat starter labeled "Karn, build me a deck from my collection."

The user-message context gets:
- Full `COLLECTION SUMMARY` block
- `## CONSTRAINED TO OWNED CARDS` block listing owned oracle IDs
  (truncated to ~2000 / ~50 KB max)

Karn's response engine pre-filters card suggestions to that set. Cards
outside it appear in a separate **Stretch goals** section with current
prices, clearly marked as not-owned.

### Tibalt collection roast

New endpoint `/api/tibalt/roast-collection`. Sends Tibalt:
- Summary block
- Outliers: most-owned single card, weirdest single-copy inclusion,
  biggest color gap, most expensive card not in any deck

Returns ~200 words of surgical disrespect. Saves to
`collection-roasts.json` so Tibalt can compare drift over time. "Six
months ago you had 23 Sol Rings. Now 31. Help."

## Cross-Deck Tracking

Computed on read, not stored. On every load of `CollectionView` or a
deck view:

```js
const collection = await loadCollection();
const decks = await loadDecks();
const conflicts = computeConflicts(collection, decks);
```

`conflicts` returns rows where `sum(deck uses) > collection.quantity`
(summing across all stacks of all printings of that oracle id).

**Memoization**: `conflicts()` is memoized on the tuple
`(collection.updatedAt, decks.updatedAt)` so re-renders within a single
state cycle don't recompute. At 30 decks × 100 cards + 5000-card
collection that's ~8000 ops per call — fast, but no reason to do it
every render.

UI surfaces:
- Grid card badge: red dot if conflicted ("used in 4 decks, own 2")
- Deck view: warning at the top listing conflicts
- Collection bottom drawer when conflicts exist: full list with
  jump-to-deck links

Why on-read: deck contents change constantly. Storing this would create
sync bugs.

## CSV Import

Two formats supported in v1.

### Deckbox

Header signature: presence of `Edition` and `Foil` columns.

```
Count,Name,Edition,Condition,Language,Foil,Signed,Artist Proof,...
```

Foil column: `"foil"` = foil, empty = nonfoil. Deckbox doesn't track
etched.

### Moxfield

Header signature: presence of `Tags` and `Last Modified` columns.

```
"Count","Name","Edition","Condition","Language","Foil","Tags","Last Modified"
```

Foil column: `"foil"`, `"etched"`, or `"non-foil"`. Maps directly to
stack finish.

### Flow

1. User uploads CSV via `CollectionImportModal`.
2. Backend (`collectionCsvImport.js`) detects format from header.
3. Per row, match against `printingIndex` via
   `${setCode}:${collectorNumber}`. If no collector number column,
   fall back to name + set. If neither matches → unmatched.
4. Preview screen: N matched, M unmatched, X merged into existing rows.
5. **Unmatched resolution UI**: list of unmatched rows. Per row, user
   can:
   - Type to search and select a specific printing
   - Click "skip" (don't import this row)
   - Click "match by name only, any printing" (uses most-recent printing
     of that oracle name)
   - Bottom action: "Skip all unmatched"
6. User confirms. Write happens via `writeCollectionAtomic`. Final
   toast: "Imported N cards (M skipped)."

Performance: 500-card CSV completes in under 10 seconds. Parser is
streaming. Lookups are O(1) against the in-memory `printingIndex` Map.

## Price Tracking

Source: bundled Scryfall `prices.usd`, `prices.usd_foil`,
`prices.usd_etched` preserved in `printings-index.json`.

Writer: sync pipeline only. After each sync, the sync script writes one
`collection-prices.jsonl` entry per owned `scryfallId`.

Reader: the app process only. Streaming line parser so multi-year
history doesn't load the whole file.

**Compaction**: entries older than 90 days are rolled up to monthly
summaries in `collection-prices.compact.jsonl`. The sync script (which
already runs periodically) handles compaction. The daily-granularity
file stays bounded.

Stats endpoint `/api/collection/stats` computes:
- Current total value (sum over owned cards × current snapshot)
- Delta vs. 30 / 90 / 365 days ago (if data exists)
- Top gainers / losers in last 30 days

UI: quiet stat block on Collection home. "Your collection is worth
$4,832. Up $147 this month." Tasteful, not financial-advisor-y.

## Wishlist

Same schema. `wishlist: true`, all stacks with `quantity: 0`. The stack
indicates which finish is wanted:

```jsonc
{
  "scryfallId": "...",
  "stacks": [{ "finish": "foil", "quantity": 0, "condition": null }],
  "wishlist": true
}
```

Filter view: "Wishlist." Shows wanted cards with current price. Total
wishlist cost displayed at the top: "Your wishlist would cost $234."

Wishlist cards get price-watched too. "Rhystic Study on your wishlist
dropped $5 this month."

When the user acquires a wishlist card (updates stack to quantity > 0),
the row is updated: `wishlist: false`.

## Open Questions

1. **Stretch goals in "build from collection" Karn mode**: should Karn
   suggest cards not in the collection? **Yes**, with a clear separate
   section. The deckbuilder use case demands it.
2. **Duplicate-on-import handling**: warn or auto-merge? **Auto-merge
   quantities** with a summary in the preview.
3. **Foil/nonfoil/etched same row or separate?** **Same row, stacks
   array** with per-stack finish + condition. Clean schema, no
   duplicate detection logic.
4. **Cross-deck conflict UI**: badge on grid vs. drawer only? **Both.**
   Badge for at-a-glance, drawer for the full list.
5. **Tibalt roast persistence**: one-shot or save? **Save** to
   `collection-roasts.json` for drift comparison over time.
6. **Per-stack condition editing UI**: bulk-edit ("set all my non-foils
   to NM") in v1? **No.** v1 edits per-stack via card detail drawer.
   Bulk edit is v2.
7. **DFC / MDFC / transform card art**: which face renders in the grid?
   **Top-level `image_uris.art_crop` if present, else
   `card_faces[0].image_uris.art_crop`**. Card detail drawer shows both
   faces.
8. **Tokens and emblems**: include in collection? **Include if user
   adds manually.** Default grid filter excludes `layout: "token"`;
   user can toggle on.
9. **Basic land stacks**: the grid showing 200 Forest entries is bad.
   **Group by oracle_id when quantity > 20 for basic lands** (use
   Scryfall `type_line` containing "Basic Land"). Display as one cell
   with quantity badge.
10. **Wishlist + foil semantics**: a wishlist row MUST have at least
    one stack with `quantity: 0` indicating the wanted finish.
    Defaults to nonfoil if user doesn't specify.
11. **First-launch wizard integration**: does it prompt for collection
    CSV? **No.** First-launch stays focused on decks + Ollama setup.
    Collection import is a separate action in the Updates / Collection
    panel post-first-launch. Wizard integration is v2 polish.
12. **Multi-window concurrent writes**: dev mode can have two tabs.
    Production `.exe` has single-instance enforcement. **Rely on
    atomic-write (temp + rename); last writer wins.** Documented as
    "do not run two dev tabs against the same data dir."
13. **Art crop image source**: bundled (large, fully offline) or
    Scryfall CDN (small bundle, requires network on first view)?
    **Decision: bundle the slim
    `printings-index.json` with `artCropPath` pointing to a separate
    bundled directory of art crops, IF this fits in the ≤25 MB budget.
    If not, lazy-fetch from Scryfall CDN on first view with a local
    cache directory under AppData (one-time network call per card,
    then offline forever).** Final call deferred to Step 0
    implementation when actual file sizes are measurable.

## Success Criteria

- Add a card via search-to-add: under 5 seconds keystroke to saved
- 5,000-card grid renders at 60fps via `@tanstack/react-virtual`, art
  crops lazy-loaded
- All Karn suggestions in any conversation show correct owned /
  needed annotations
- Karn's total user-message-context token count stays under 16K with
  collection summary injected (measured via `inputCharCount`)
- CSV import of 500-card Deckbox export completes in under 10 seconds
  with clean preview
- Cross-deck conflict detection runs in under 100ms when opening a
  deck view (memoized)
- Tibalt collection roast returns within 30 seconds on Ollama
- "Build from my collection" Karn mode returns 100-card list in under
  60 seconds with proper owned / stretch goal split
- Wishlist persists across launches and price-tracks on each sync
- Schema migration: app refuses to load `version > 1` with a clear
  error message
- Corrupted file: app backs up + starts empty + shows toast warning

## What This Unblocks

Once Collection ships:

- **Bracket coach** (next theme) becomes realistic. Bracket suggestions
  can recommend "to push this from bracket 2 to bracket 3, add these 5
  cards, you own 3 of them already."
- **Evolution memory + weekly digest** gets a richer signal. Snapshots
  include collection state, not just deck state. "You acquired 7 cards
  this week. Three of them slot directly into your Atraxa list."
- **Pod simulator** lets you test decks built from real cards.
- **Camera scan** (physical bridge phase) plugs directly into the
  collection schema — same stacks model, scan-to-add becomes a new
  Add path.
- **Notebook + local social** reference cards you own, which makes
  references mean something.

## Appendix: The Full Roadmap

For reference, the broader plan from this office hours session, in
order. Each phase ships independently. Each builds on the one before.

1. **Collection** (this doc) — Foundation. Karn learns what you own.
2. **Bracket coach + Evolution memory** — Bracket assessment, weekly
   Ollama-generated deck digest, drift detection.
3. **Pod simulator** — Tibalt / Karn / Jace become 3 opponents.
   Garfield grows from goldfish to four-player.
4. **Physical bridge** — Webcam card scan into Arbiter + Collection.
   Voice mode (Whisper + Piper) for paper games.
5. **Notebook + Local social** — Capture rulings, plays, future deck
   ideas. Pod tracking. Friend deck library. Jace-voice game recaps
   from the game log.

None require external services. All compound on the four moats:
bundled Scryfall data, local Ollama compute, structured game log
infrastructure, automated weekly release pipeline.
