### UX issues (14)

- Three near-identical 'onboard the user' surfaces overlap: OnboardingWizard modal, the legacy bootstrap banner (MTGAssistant.jsx:959-1036), and the Ollama health banner (MTGAssistant.jsx:1042-1148) can all be relevant on the same fresh install simultaneously, each with its own distinct color palette and its own text-input/button pattern for what is functionally the same 'import my old data' or 'set up my model' task.

### UX issues (12)

- DeckConfirmModal and PodBalanceModal both hand-roll every button's style inline instead of using the shared pb() helper that DeckView.jsx and ImportDeckView.jsx use — three separate button visual languages exist across four files in this one audit alone (pb() family, DeckConfirmModal's bespoke transparent/filled trio, PodBalanceModal's GOLD-CTA + row-as-button pattern).
- DeckConfirmModal's three action buttons ('Chat without a deck', 'Import a deck', 'Confirm & start') have no visual hierarchy differentiation beyond color — all three are same size/padding/radius, so the primary action (Confirm & start, only shown once a deck is picked) doesn't read as more prominent than the opt-out button; a user could easily click 'Chat without a deck' by habit after actually picking a deck.
- DeckConfirmModal is explicitly non-dismissable (no backdrop click, no Escape) per the file's own header comment — every exit is a deliberate button, which is good intent, but combined with zero saved decks + no onImport wiring this becomes a real dead end (only escape is 'no deck').
- DeckView's empty state ('No deck loaded') leaves the user on a nearly bare ribbon with only Chat/Export buttons and no in-view call-to-action to import or select a deck — the only path forward is the sidebar, which isn't visible in this file and isn't hinted at in-view.
- The 'x' delete button on Game Log entries (DeckView.jsx:612) is a single mystery-meat glyph with no confirm dialog, no hover state defined, and no aria-label — inconsistent with every other destructive action in the same file (Delete snapshot at :507 is a labeled text button, also with no confirm, but at least says 'Delete').
- Snapshot Delete (DeckView.jsx:507) and Restore (DeckView.jsx:504, which DOES confirm via browser confirm()) are inconsistent about confirmation — Restore guards against data loss with a native confirm(), Delete does not, despite both being irreversible.
- PodBalanceModal's per-deck picker row is a full <button> wrapping a fake checkbox span (14x14 div with a raw ✓ character) — this is a custom checkbox that doesn't use any native input, has no keyboard/screen-reader affordance beyond whatever the outer button provides, and duplicates a pattern that could just be a real checkbox input.
- Website-not-appliance smell: DeckView's decklist rows (both populated-deck path :338-343 and orphan-deckCards path :644-649) open scryfall.com/search in a new browser tab via window.open() — this punts the user out of the desktop app into their web browser for basic card lookup, when the app's own local Scryfall data (mandated by CLAUDE.md §1.1/§1.2) could drive an in-app card preview instead of an external site round-trip.
- ImportDeckView's manual-paste title text color (#cec8e0, DeckView.jsx-sibling ImportDeckView.jsx:81) is hardcoded and ignores the `colors` prop entirely, unlike literally every other text color in the same file — a leftover/inconsistent styling artifact.

- Version History panel mixes THREE different micro-button sizes/paddings in close proximity: SectionHead-level ('4px 8px', :450/:452), per-snapshot-row-level ('3px 7px', :504/:506/:507) — no evident sizing system, just ad hoc shrinking per nesting depth.

### UX issues (12)

- Two entirely separate game-UI implementations coexist: LearnBoard (visual, primary) and LearnView's own inline legacy two-column DecisionPrompt/aside layout (only shown when session.board is falsy). The legacy path still fully implements every decision-panel wiring redundantly and uses the app's colors/cfg tokens while LearnBoard ignores them completely — an overhaul must decide whether the legacy path is dead code to delete or a real fallback to redesign.
- LearnBoard.jsx is a fully self-contained visual system (its own <style> block, own color palette, own 'GOLD' constant) with zero connection to the app's globals.css var(--*) tokens or the colors/cfg props passed down from the shell. Any global theme change (the Aether→Leyline swap this task exists for) will not touch this surface at all unless LB_CSS is rewritten by hand.
- Side-sheet stacking is manually coordinated rather than systematized: the unresolved-Arbiter sheet is z-40 at right:16/width:372, the tutor/clone/scry/etc. sheets are z-45 at right:16/width:440 (same position, different z so they'd visually collide if both could appear — only one decision.kind is ever active at a time so this happens to work, but there's no shared overlay/stacking primitive), and the Ask-Jace pop-out manually shifts itself right:18→404 + z:20→45 specifically to dodge the unresolved sheet. Adding a 14th decision kind requires hand-tuning geometry against all the others.
- The floating engine-error banner's only stated remedy is 'use Abandon game below to start over' (LearnView.jsx:579) — a hard dead end with no retry, no reconnect, and 'below' refers to a footer button that does not exist in the LearnBoard (primary) rendering path at all (that footer is only rendered in the legacy branch) — so in the actual primary UI the error text points to a button the user cannot see.
- 9 side-sheet panels (TutorSearch, HandDiscard, ImpulseDig, SacrificeChoice, DiscardChoice, CloneCopy — plus structurally SacrificeChoice/DiscardChoice are near-identical to each other) duplicate the exact same ~90 lines of art-grid-select-submit JSX and inline styles with only copy/labels differing. This is a strong 'extract a shared CandidatePickerPanel' candidate but currently each is a hand-maintained copy, so a visual-language change means editing the same pattern 9 times.
- 3 panels (SoftCounter, OptionalManaPayment, OptionalSac) and 2 more (OptionalChoice, CommanderReturn) are near-duplicate yes/no shapes with two different button-fill conventions (solid-fill pair vs outline-on-BG3 pair) for what is conceptually the same 'pay or decline' interaction — inconsistent affordance for the same interaction pattern.
- Mystery-meat icon-only header button: the idle screen's 'Stress test → Sim Center' button (LearnView.jsx:206-224) exists only as an escape hatch pointing to a totally different app section (setCenterView('sim')) — it reads as an in-place feature but is actually a cross-navigation link with no visual distinction from a same-page action.
- '⚖ Rules check' / Arbiter unresolved-panel copy ('The simulator can't fully model this card yet, so rather than guess it asked the Arbiter...') exposes an internal engineering limitation directly to the end user as normal in-game flavor — website-not-appliance energy; a finished kiosk-feel product would not surface 'the engine gave up, ask a fallback AI' language as a first-class game moment.

- Two different 'gold' constants exist simultaneously and are used inconsistently: the app-wide cfg.color/GOLD prop (used throughout LearnView's inline styles) vs LearnBoard's own hardcoded GOLD='#c9a14e' fallback / --gold CSS var (LearnBoard.jsx:77, ignores the colors.GOLD value passed in except as a fallback default) — these can drift out of sync since LearnBoard only reads colors.GOLD, not the full cfg object other panels use for accent.

### UX issues (11)

- Deck-load error state (SimCenter.jsx L265-266) has no retry button — the fetch only runs once on mount, so a transient failure strands the user with no way to re-trigger it short of leaving and re-entering the section (if that even remounts) or reloading the app.
- Empty deck-library state (SimCenter.jsx L267-270) is a dead end: text says 'import a deck first, then come back' but there is no button/link to jump to the deck-import flow from here — pure prose, no affordance.
- Run error state (SimCenter.jsx L417) has no explicit 'Try again' / retry button distinct from re-clicking the same Run simulation button lower on the page — the error and the retry action are spatially disconnected (error renders after the run button in DOM order, so the fix-it action is actually ABOVE the error message, which reads backwards).
- The saved-report viewer modal (SimCenter.jsx L504-535) only closes via backdrop-click or the × button — no Escape-key handler, which is a common expected affordance for modal dismissal and its absence is inconsistent with typical desktop-app conventions this kiosk app should be emulating.
- Six visually distinct 'selectable card' patterns exist for what are conceptually 2-3 interaction types (deck checkbox card, radio-format card, radio-pairings card, plain bank-data checkbox with no card, ghost buttons, outline button) — the bank-training-data checkbox conspicuously breaks the established checked-card visual language used everywhere else in the same file (deck picker, format/pairings radios all use bordered cards; this one is bare text+checkbox), which reads as an inconsistency within a SINGLE component, not just cross-component drift.
- Ghost button treatment (padding 4px 10px, font 11px) is reused for five semantically different actions (bulk-select toggle, bulk-select-scoped-to-profile toggle, list refresh, open-report navigation, and file download) with zero visual differentiation between 'toggles a selection state' vs 'navigates/opens a modal' vs 'downloads a file' — a user cannot predict from styling alone whether a ghost button will change local state, open new UI, or trigger a file save.
- The Run-simulation button's disabled state uses `background: LINE` with `opacity: 0.6`, which on a dark theme produces a very low-contrast, hard-to-read disabled affordance — likely fails WCAG contrast minimums and doesn't clearly communicate WHY it's disabled (no tooltip; the explanatory helper text is a separate conditional span that only appears when 0 < selected < minDecks, so at 0 selected decks the button is simply grey with no adjacent explanation).
- Close button in the saved-report modal (SimCenter.jsx L521) is a bare '×' glyph in a plain unstyled button (no border, no hover-state background, no radius) — this is the only 'mystery-meat' close affordance in the file; every other action has a text label, but this one relies purely on iconographic convention with no visual weight/click-target padding, which reads as a copy-pasted web pattern rather than a considered kiosk-app control.
- StabilityBadge's 'absence = stable' design means there is genuinely no way to tell 'stable feature' apart from 'no badge was ever wired up' from the UI alone — a developer forgetting to add a badge to a genuinely rough feature is indistinguishable from a deliberately-marked-stable feature; this is a latent trust-signal risk, not a rendering bug, but worth flagging since the whole badge system depends on 100% correct opt-in tagging.
- Bank-training-data section (SimCenter.jsx L369-384) is wrapped in the generic `card()` helper (BG3 background, LINE border, 8px radius, 14px padding) which is a one-off use in this file — so this section visually reads as 'special/highlighted' relative to the Format/Pairings fieldsets right above it, even though it's not more or less important than run configuration, just because it happens to be the only section using the `card()` wrapper.
- Sparkline.jsx renders `null` for fewer than 2 data points with zero placeholder/skeleton — if embedded next to a price label elsewhere in the app, this produces an unexplained blank gap rather than a 'no price history yet' indicator, which is a website-widget silent-failure pattern rather than an appliance-grade empty state.

### UX issues (12)

- OnboardingWizard has no re-entry point once dismissed (onFinish sets a marker, no button anywhere in the shell reopens it) — a user who skips setup and later wants to install Ollama or import a previous install's data has no discoverable path back to that flow; they must know to use Settings > Models and the OnboardingWizard's own 'restore from previous install' step is simply lost forever.
- SettingsModal has two separate buttons in two separate tabs (Privacy and Data & Updates) both labeled identically 'Open Data & Updates →' that do the exact same thing — redundant navigation that suggests those two tabs should be merged or cross-referenced instead of duplicated.
- ProfileManageModal's Rename and Delete actions drop out of the styled UI entirely into native window.prompt()/window.confirm() dialogs — jarring OS-chrome popups in the middle of an otherwise fully-custom-styled app, breaking the 'appliance, not a website' feel the LEYLINE pass targets.
- UpdatesModal's 'Show me updates before installing' toggle reads/writes localStorage directly inside the render body (three separate try/catch IIFEs called synchronously during JSX construction) rather than using React state — functionally fragile (no re-render triggers reliably on toggle, relies on setAppUpdate({...prev}) as a hacky force-update) and a pattern that should not survive the LEYLINE refactor.
- UpdatesModal cannot be closed while a sync is running (the × is swapped for Cancel, and clicking the backdrop is guarded by `!busyAction`) — reasonable to prevent losing sync state, but there's no way to minimize/background it visually; the user is stuck staring at the modal for a 10-15 minute Spellbook sync with only the log pane for company.
- FeedbackPanel's floating 💬 button is present on literally every screen with zero way to hide/dismiss it — for a 'kiosk appliance' feel this permanent floating chrome-element competes with in-app content on every surface (chat, decks, Academy, Sim) and was flagged by name in the LEYLINE orders as something to reconsider for the shell wave.
- FeedbackPanel's pop-out button and Cmd/Ctrl-Shift-F shortcut are silently absent in the Tauri .exe (by design, since window.open() escapes to the system browser there) — desktop-app users lose the 'send feedback from a second monitor while working' capability with zero UI acknowledging it was ever available; the feature quietly vanishes rather than being replaced with a Tauri-native equivalent (e.g. a second WebviewWindow).
- FeedbackWindowApp (the /feedback-window popup) hard-codes its own separate copy of the entire color theme instead of consuming shared tokens or the shell's `colors` prop — any future LEYLINE token change must be manually re-applied to this file a second time or the popup will silently drift out of sync with the rest of the app.
- Two structurally near-identical 'gold-fill primary button' helpers exist side-by-side in OnboardingWizard.jsx (Btn() and primary()) with different padding and no functional distinction — signals the component was built by copy-paste-tweak rather than a shared button primitive, exactly the kind of drift the LEYLINE button-system pass should collapse.
- UpdatesModal's blue #244a7a/#4a7ac4 'primary action' button family (Refresh all, Download & Install, autostart-enabled) is a completely different hue from the cyan/GOLD (#00dbe7-family) primary used in every other owned surface — this is the single biggest color-language inconsistency across the owned files and will be very visible once the rest of the app is retokenized to LEYLINE while this modal (if untouched) keeps its blue accent.
- ProfileGate is a full-screen, non-dismissible gate with no back-out — if profiles.length===0 and stays empty (e.g. server error not surfaced as `error`), the user is stuck on 'Setting up your profile…' with only the dashed '+ New / Manage' tile as an escape hatch and no visible way to retry/refresh; there's no timeout or retry affordance in the component itself.
- Mystery-meat glyph-only buttons: '⧉ Pop out' (FeedbackPanel), '⟳ Updates' / '⚙ Settings' (AppHeader, referenced from owned modals' reach paths), and '×' close buttons throughout rely on hover title= tooltips for meaning, which are invisible on first glance and non-existent on touch/mobile — several owned modals (Updates, Settings, ProfileManage) use bare '×' with no aria-label in some instances (UpdatesModal.jsx:466-470 has neither aria-label nor accessible text, just title).

**Risks:**
- No code in lib.rs reads, sets, or depends on the window TITLE STRING itself — title is purely declarative in tauri.conf.json and never touched programmatically. Changing the title text (e.g. to add a version suffix) is zero-risk to lib.rs.
- All window lookups in lib.rs use the window LABEL "main" (via app.get_webview_window("main")) in six call sites: single-instance focus handler (line 197), autostart-hidden-launch check (line 220), tray-show (line 251), tray-hide (line 258), tray-icon-click toggle (line 284), plus the on_window_event closure (line 475) which receives the window directly from the event. As long as the window's `label` stays "main" in tauri.conf.json, none of these break from a decorations/chrome change.
- The CloseRequested handler (lib.rs line 480) is decoration-agnostic — it fires on ANY close request regardless of native vs custom chrome, AS LONG AS the custom close button in a new title bar invokes the standard window-close API rather than a direct exit/destroy call. This is the single most important behavioral contract to preserve when building custom chrome: a naive custom close button that calls app.exit() or window.destroy() instead of window.close() would silently break the hide-to-tray UX (this is a frontend-implementation risk, not an existing lib.rs risk — lib.rs itself needs no changes for this to keep working correctly, assuming the frontend does it right).
- No WindowBuilder is ever constructed in lib.rs — the window is 100% declared in tauri.conf.json and referenced only by label at runtime. This means decorations:false is a config-only change from lib.rs's perspective; Rust-side risk is effectively zero. All real risk and implementation cost sits in the Next.js frontend, which does not yet have any custom title-bar/drag-region/window-control code (none exists in the reviewed files — this would be new frontend surface, not a retrofit).
- The 2-minute timeout error message in frontend-placeholder/index.html (line 59-64) hardcodes 'MTG Tool' branding text and instructions referencing launch.log — if a custom title bar / new visual theme is applied to the real app but NOT to this placeholder, there will be a visual mismatch/flash between the old generic dark loading screen and the new kiosk-themed app for the ~1-30s the placeholder is visible on every launch. This file was not asked to be modified but is a visible inconsistency risk worth flagging for the surface-waves phase.
- frontend-placeholder/index.html is unaffected by decorations:false and does not need edits for the chrome change itself — it's a plain content page inside whatever window chrome exists, native or custom. It only needs updating if visual consistency with the new theme is desired (separate concern from the title-bar mechanics).
